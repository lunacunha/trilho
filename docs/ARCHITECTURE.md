# Trilho — Architecture

_Version 1.0 · 15 Nov 2026_

## 1. Overview

```
Browser ──► Vercel (fra1) ──► Next.js app ──► Neon Postgres (Frankfurt)
                                   │
                                   └──► Gmail SMTP (verification emails)
```

One Next.js application serves the UI and the server logic. Data lives in a Neon Postgres database. Every push to `main` on GitHub deploys to Vercel.

## 2. Stack

| Concern | Choice |
|---|---|
| Framework | Next.js (App Router) + TypeScript |
| UI | React Server Components, Tailwind CSS, Chart.js (dashboard) |
| Database | Neon Postgres 18 (EU, Frankfurt) |
| ORM / migrations | Drizzle ORM + drizzle-kit |
| DB driver | `@neondatabase/serverless`: HTTP (`drizzle-orm/neon-http`) for queries and Better Auth; a WebSocket `Pool` per transaction via `withTransaction` in `db/client.ts` (decision 041) |
| Auth | Better Auth (email + password, email verification) |
| Validation | Zod |
| Email | Nodemailer + Gmail SMTP |
| Tests | Vitest |
| Hosting | Vercel (Hobby), functions in `fra1` |

## 3. Layers

Each layer only calls the layer below it.

```
1. UI          app/ pages, components/      Shows data, collects input. No business logic.
2. Entry       Server Actions, Route        Reads the session, validates input (Zod),
               Handlers (app/api)           calls one service. Thin.
3. Services    lib/services/                Business logic: permissions, rules, transactions,
                                            product events.
   Rules       lib/rules/                   Business rules R1–R12 as pure functions.
4. Data        db/                          Drizzle schema, DB client, migrations, seed.
```

**Why:**
- **Rules are pure functions** (input in, result out, no database, "today" passed as a parameter). They are unit-tested with the exact examples in SPEC.md.
- **Services hold the business logic**, so the UI today and a public API in later assignments call the same code.
- **The UI never queries the database directly**, so permission checks cannot be skipped.

## 5. Request flows

**Writing — a student saves a new application (US02)**
1. The form in `app/applications/new` submits to a Server Action.
2. The Server Action reads the session (who is the user?) and validates the input with the Zod schema.
3. It calls the `applications` service → `createApplication(user, input)`.
4. The service finds or creates the company (R11), inserts the application and the initial status change **in one transaction**, and records `application_created`.
5. The Server Action redirects to `/pipeline`.

**Reading — a student opens the pipeline (US03, US05)**
1. The page (a Server Component) reads the session.
2. It calls the `applications` service → `getPipeline(user, today)`.
3. The service applies R5 (60 days), loads the student's applications, computes days since sent (R10) and reminders (R4, using company statistics R2–R3), and records `reminder_triggered` for new reminders.
4. The page renders the columns.

## 6. Authentication and authorization

- **Authentication:** Better Auth. Registration is restricted to `@up.pt` / `@fe.up.pt`; login requires a verified email.
- **Route protection:** pages for logged-in users redirect visitors to `/login`; students who have not answered consent are redirected to `/onboarding/consent`.
- **Authorization lives in the services:** every service function receives the current user and checks ownership (a student only touches their own applications) or role (`career_service` for the dashboard). Hiding a button in the UI is convenience, not security.

## 9. Testing strategy

- **Unit tests** (`tests/unit/`): every business rule, using the numeric examples from SPEC.md.
- **Integration tests** (`tests/integration/`): services against the `test` database branch — permissions, consent filtering, cascading deletes.
- **Manual tests:** every screen checked by hand before each release, including at 375 px width.
- Test names include the scenario ID from SPEC.md (e.g. `US02-6`).

## 10. Deployment

1. Push to `main` on GitHub.
2. Vercel builds (`npm run build`) and deploys automatically.
3. Database migrations are run explicitly against the `production` branch before deploying a change that needs them.
4. `/api/health` confirms the app and the database are up.
