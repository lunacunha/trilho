## What this project is

Trilho: a shared job-application tracker for FEUP master's students, with anonymous company response times and a Career Service dashboard. MVP for the Information Systems Architecture course (MESG, FEUP).

**Sources of truth — read before coding:**
- `SPEC.md` — stories, acceptance scenarios (IDs like `US02-6`), business rules (R1–R12), statuses, fixed lists, events.
- `docs/ARCHITECTURE.md` — layers, folders, request flows.
- `docs/decisions.md` — why things are the way they are.
- `docs/product/mvp-scope.md` — what is in and out of scope.

If something is ambiguous or missing in `SPEC.md`, **stop and ask**. Never invent a business rule.

## Stack

Next.js (App Router, no `src/`) · TypeScript (strict) · Tailwind CSS · Drizzle ORM + drizzle-kit · Neon Postgres (`@neondatabase/serverless`) · Better Auth · Zod · Nodemailer (Gmail SMTP) · Chart.js · Vitest · Vercel.

## How to work

1. Work on **one story (vertical slice) at a time**. Name the story ID.
2. Before changing more than one file, **propose a short plan** (files to touch, approach, tests) and wait for approval.
3. Write or update the tests for the scenarios involved, then implement.
4. Verify (see "Definition of done") and report.

## Architecture rules

- Layers: UI (`app/`, `components/`) → entry (Server Actions, Route Handlers) → services (`lib/services/`) → data (`db/`). A layer only calls the one below it.
- **No database access in pages, components or Server Actions.** Only services touch `db/`.
- **Business rules live in `lib/rules/` as pure functions**: no database, no `new Date()` inside — "today" is a parameter.
- **Authorization is checked in services**: every service function receives the current user and checks ownership or role. Hiding UI is not security.
- Validate every input on the server with the Zod schemas in `lib/validation.ts`.
- Writes that touch more than one table run in **one transaction**.
- Product events (SPEC §9) are recorded only through `lib/services/events`.
- Statistics are calculated on request and never cached (consent changes take effect immediately).

## Database rules

- Change tables only in `db/schema.ts`, then generate a migration with `npm run db:generate`.
- **Never edit a migration that has already been applied.** Create a new one.
- **Never run migrations or seeds against the `production` branch** unless explicitly asked.
- Seed data is fictional and labelled as such (fictional company and person names).

## Testing rules

- **Every change comes with tests.** No exceptions for business rules.
- Test names start with the scenario or rule ID: `it("US02-6: links ' lumen  ENERGY ' to the existing company", ...)`, `it("R2: median 17 days → '2–3 weeks'", ...)`.
- Rule tests use the numeric examples from `SPEC.md`.
- Tests run against the Neon `test` branch only — never `dev` or `production`.
- A test that fails must fail for the right reason; never weaken a test to make it pass.

## Dependencies

**Do not add dependencies without asking.** Approved: `next`, `react`, `tailwindcss`, `drizzle-orm`, `drizzle-kit`, `@neondatabase/serverless`, `better-auth`, `zod`, `nodemailer`, `chart.js`, `vitest`, and their type packages.

## Security

- Never read, print, edit or commit `.env*` files (except `.env.example`, which has names only).
- Never log secrets, passwords or tokens.
- Never loosen an authorization or consent check to make something work.
- Errors shown to users are short and actionable; technical details only go to server logs.
- Never use real-looking email addresses in tests, seeds or smoke tests. Use `example.com` addresses, or the developer's own address when a real email must be received.

## Conventions

- English everywhere: code, comments, UI text, commit messages.
- TypeScript strict; no `any`.
- Files: `kebab-case.ts`; React components: `PascalCase`.
- UI: Tailwind; every input has a label; works with the keyboard; usable at 375 px width.
- Commits: Conventional Commits with the story ID, e.g. `feat(US02): create application form`, `test(R2): typical range rounding`.

## Definition of done

A change is done only when:
1. `npm run lint`, `npm test` and `npm run build` all pass.
2. The affected screens were checked by hand (the report says what to check).
3. Errors are handled with a useful message.
4. The report lists: what changed, which scenario IDs are covered by tests, and anything left open.

Never modify `SPEC.md`, `docs/decisions.md` or `AGENTS.md` without asking.
