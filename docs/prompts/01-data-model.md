## Decisions already made

**IDs and types**
- Our tables use UUID primary keys (`defaultRandom`). Better Auth tables keep Better Auth's own id type; our FKs to `user.id` match it.
- Timestamps: `timestamp with time zone`. `date_sent` and `changed_on`: `date`.

**Database connection**
- `db/client.ts` must use `drizzle-orm/neon-serverless` with a `Pool` (WebSockets), **not** `neon-http`, because services need interactive transactions (CLAUDE.md).
- If `drizzle-kit` needs a direct (non-pooled) connection for migrations, propose an extra variable `DATABASE_URL_UNPOOLED`.
- Load env vars with `@next/env` (already installed with Next.js). Do not add `dotenv`.

**Enums (Postgres enums)**
- `application_status`: `sent`, `in_process`, `interview`, `offer`, `rejected`, `no_response`
- `reminder_reason`: `company_median`, `fallback_14_days`
- `reminder_outcome`: `followup_done`, `dismissed`
- `event_name`: `application_form_opened`, `application_created`, `reminder_triggered`, `reminder_followup_done`, `reminder_dismissed`

**Tables**
| Table | Columns | Keys, constraints, indexes |
|---|---|---|
| `user` (Better Auth) + extra fields | Better Auth columns + `role`, `consent`, `consent_updated_at` | `role`: `student` or `career_service`, NOT NULL, default `student` (enum or CHECK — choose what works with Better Auth and explain). `consent`: boolean, NULL = not answered yet. |
| `session`, `account`, `verification` | Better Auth columns | As generated by Better Auth. |
| `company` | `id`, `name`, `normalized_name`, `created_at` | `normalized_name` UNIQUE (R11). |
| `sector`, `channel`, `job_type` | `id`, `name` | `name` UNIQUE. Values from SPEC §5. |
| `application` | `id`, `user_id`, `company_id`, `sector_id`, `channel_id`, `job_type_id`, `role_title`, `date_sent`, `current_status`, `created_at`, `updated_at` | `user_id` → user ON DELETE CASCADE. `company_id`, `sector_id`, `channel_id`, `job_type_id` → ON DELETE RESTRICT. `role_title` NOT NULL, CHECK length 1–120. `current_status` NOT NULL, default `sent`. Indexes on `user_id`, `company_id`. |
| `status_change` | `id`, `application_id`, `status`, `changed_on`, `is_automatic`, `created_at` | `application_id` → ON DELETE CASCADE. `is_automatic` NOT NULL default false (true only for R5). Index on (`application_id`, `changed_on`). |
| `reminder` | `id`, `application_id`, `status_change_id`, `reason`, `threshold_days`, `triggered_at`, `outcome`, `outcome_at` | Both FKs ON DELETE CASCADE. `status_change_id` UNIQUE (one reminder per quiet period, R12). `outcome` nullable. |
| `product_event` | `id`, `user_id`, `name`, `application_id`, `properties` (jsonb), `created_at` | `user_id` → ON DELETE CASCADE (decision 027). `application_id` → ON DELETE SET NULL. Index on (`name`, `created_at`). |

- Company name length (1–120) is a CHECK. "Date sent not in the future" is **not** a CHECK (it depends on today); it stays in Zod later.
- `application.current_status` duplicates the last `status_change` on purpose (fast pipeline). The seed must keep both consistent.

**Seed**
- Deterministic: a fixed-seed pseudo-random generator written inline (no new dependency). Dates are relative to the day the seed runs, so the demo always shows current cases.
- Re-runnable: it first deletes all Trilho data (our tables and the seeded users), then inserts. Running it twice gives the same counts. Print the database host before writing.
- Users are created through Better Auth, so passwords are hashed. All seeded users have a verified email. Password from env var `SEED_PASSWORD` (fail with a clear message if missing).
- Accounts:
  - 1 Career Service: `careers@fe.up.pt`, role `career_service`.
  - 1 demo student for the live demo: `demo@up.pt`, consent `true`, with applications in every pipeline column.
  - ~25 fictional students: "Demo Student 01…25", `demo.student01@up.pt`…, ~75% consent `true`, the rest `false`.
- ~12 fictional companies (use the names from the Assignment 1 mockups: Northwind Consulting, Lumen Energy, Atlântico Retail, Douro Software, Ferro Industrial, Vela Logistics, Brisa Bank, Mar Telecom, Norte Health, plus 3 more fictional names). Distribution:
  - at least 4 companies **with** a statistic (≥ 5 replied applications from consenting students, R3);
  - at least 3 companies **without** one;
  - at least 1 company with fewer than 5 applications in total (to show R8 in the dashboard).
- ~200 applications over the last 120 days, with a consistent status history (first change = `sent` on `date_sent`; `current_status` = last change). Use every channel; make Career Fair appear often enough to compare.
- Cases the demo needs, on the demo account:
  - an application past its company's median → reminder (R4);
  - an application at a company without a statistic, 15 days quiet → 14-day reminder;
  - an application in `sent` with the last change 70 days ago → R5 will convert it when the pipeline loads (do **not** pre-apply R5);
  - at least one application in each status.
- Product events consistent with the data, so every metric in `docs/product/mvp-scope.md` §6 returns a number: form opened/created pairs (with durations of 10–90 s, some forms abandoned), reminders with outcomes.
- All names are fictional and clearly labelled "Demo".

## Done when
- `npm run db:generate` creates the migration in `db/migrations/`.
- `npm run db:migrate` runs on an empty `dev` branch without errors.
- `npm run db:seed` runs twice in a row without errors and prints the same counts.
- `npm run lint` and `npm run build` pass.
- `docs/data-model.md` exists with the ER diagram and the tables.
