# Decision log

Short records of decisions that shape Trilho. Newest decisions at the bottom.

| # | Date | Decision | Why | Alternatives considered |
|---|---|---|---|---|
| 001 | 13 Nov | **Next.js + TypeScript** instead of Laravel | Preference for JavaScript; PHP was only required by the FEUP server, which is not used | Laravel (PHP) |
| 002 | 13 Nov | **Host on Vercel**, not the FEUP server (gnomo) | gnomo requires the FEUP VPN from outside FEUP; the app must be reachable by other applications | FEUP gnomo server, Laravel Cloud, Railway |
| 003 | 13 Nov | **Zero-cost constraint**: every service on a free plan | Student project, no budget | Paid plans |
| 004 | 13 Nov | **Neon** for Postgres, not Supabase | Neon free scales to zero and wakes in milliseconds; Supabase free pauses projects after ~7 days of low activity | Supabase |
| 005 | 13 Nov | **EU region (Frankfurt)** for database and functions | Low latency for users in Portugal; student personal data stays in the EU (GDPR) | US East (Neon default) |
| 006 | 13 Nov | **Better Auth** inside the app | User tables live in our own schema with real foreign keys; no vendor lock-in | Supabase Auth, Neon Auth |
| 007 | 13 Nov | **Gmail SMTP** for verification emails | Resend's free plan only sends to the account owner without a verified (paid) domain | Resend |
| 008 | 13 Nov | **Production env vars set manually** in Vercel, Production only | Avoid copying local values to production. Preview deployments get no database variables and never point at production (updated 22 Nov; see `docs/deploy.md`) | Import `.env` file |
| 009 | 15 Nov | **No `src/` directory** | Project was created without it; moving adds configuration changes with no benefit | Move `app/` into `src/` |
| 010 | 15 Nov | **Registration with `@up.pt` / `@fe.up.pt` email + verification** (D1) | FEUP SSO is out of reach for the MVP; verification makes the domain restriction real | FEUP SSO, open registration |
| 011 | 15 Nov | **Statistic requires ≥ 5 replied applications** (D2, R3) | Without a reply there is no response time; fixes an inconsistency in Assignment 1 | 5 applications of any kind |
| 012 | 15 Nov | **60-day rule only for Sent and In process** (D3, R5) | A process at Interview or Offer that goes quiet is a different situation | All statuses |
| 013 | 15 Nov | **Company autocomplete + name normalisation** (D4, R11) | Consistent names are needed for company statistics; merging subtler duplicates (US15) is cut | Free text, fixed company list |
| 014 | 15 Nov | **Reminders on the pipeline card only** (D5) | Notifications are out of scope (Won't) | Email reminders |
| 015 | 15 Nov | **Roles `student` / `career_service`; Career Service accounts created by the seed** (D6) | A public "I am Career Service" sign-up would be a security hole | Role chosen at sign-up |
| 016 | 15 Nov | **US14 (spreadsheet import) cut, kept as the first post-pilot iteration** | The MVP must first prove students log applications manually. If activation is low because of past applications, import becomes the next feature: a cut today that becomes a data-driven decision tomorrow | Build import in the MVP |
| 017 | 15 Nov | **Typical range = median, rounded down/up to weeks** (R2) | Simple, matches "median-based" in Assignment 1, easy to test | Interquartile range (P25–P75) |
| 018 | 15 Nov | **Reminder threshold = company median** (R4) | Starting at the median leaves "raise the threshold" as the fallback if many reminders are dismissed (H3) | Upper end of the range |
| 019 | 15 Nov | **60-day rule evaluated when the pipeline loads, backdated to last change + 60 days** (R5) | No scheduled job needed; the history still shows the correct date | Daily cron job |
| 020 | 15 Nov | **Free movement between manual statuses; change date pre-filled with today** (R6) | Students make mistakes and correct them, and often log a reply days after receiving it; a strict state machine adds friction without value | Strict forward-only transitions; change date always today |
| 021 | 15 Nov | **Dashboard shows companies and channels only with ≥ 5 applications** (R8) | A row based on one student would identify that student | No threshold |
| 022 | 15 Nov | **Layered architecture with pure rule functions and a service layer** | Rules are testable without a database; UI and future API share the same logic | Logic inside pages / Server Actions |
| 023 | 15 Nov | **Zod for validation** | One schema validates both the form and the server | Hand-written validation |
| 024 | 15 Nov | **"Today" passed as a parameter to business rules** | Tests give the same result every day | Reading the system clock inside rules |
| 025 | 15 Nov | **One Neon branch per environment** (`production`, `dev`, `test`) | Development and tests never touch real data | One shared database |
| 026 | 15 Nov | **Statistics calculated on request, never cached** | Withdrawing consent must take effect immediately (US08) | Cached statistics |
| 027 | 15 Nov | **Deleting an account also deletes the user's product events** | GDPR right to erasure; metrics lose deleted users, which is accepted | Keep anonymised events |
| 028 | 15 Nov | **Keep `AGENTS.md` (generated by Next.js) and import it from `CLAUDE.md`** | `AGENTS.md` is written and re-added by `next dev`, so it cannot be removed; it tells agents to read the installed Next.js docs. `CLAUDE.md` holds the project rules written for this project | Single merged `CLAUDE.md` |
| 029 | 19 Nov | **UUID primary keys** for Trilho tables | Sequential IDs make URLs guessable; UUIDs cost nothing extra in Drizzle | Integer IDs |
| 030 | 19 Nov | **Fixed lists as reference tables; statuses and event names as Postgres enums** | Lists are data that may grow (US15); statuses are tied to code (R4, R5) and must only change with the code | Enums for everything; reference tables for everything |
| 031 | 19 Nov | **`current_status` stored on `application` as a deliberate duplicate of the last status change** | The pipeline reads it constantly; both are updated in one transaction | Compute it from `status_change` on every read |
| 032 | 19 Nov | **`neon-serverless` driver with a `Pool`** (superseded by 048), and a direct (unpooled) connection for migrations | Services need interactive transactions, which `neon-http` does not support; schema changes are unreliable through the pooler | `neon-http`; pooled connection for migrations |
| 033 | 19 Nov | **`email_verified_at` added to the user** | Better Auth only stores a boolean; M6 needs the verification date | Derive it from events |
| 034 | 22 Nov | **R9 activity = when the student acted in Trilho** (application or status change recorded, Lisbon time), excluding automatic R5 changes | Measures real use of the app, consistent with M7 retention; typed dates would mark a student who logs old applications today as inactive | Business dates (date sent, change date); counting automatic changes |
| 035 | 21 Nov | **Sign-up and resend never reveal whether an account exists** | Knowing that a colleague has a Trilho account reveals that they are job hunting | "User already exists" message |
| 036 | 21 Nov | **The seed inserts users directly**, with passwords hashed by Better Auth, instead of signing them up | With email verification on, sign-up would send real emails to seeded `@up.pt` addresses | Sign-up through Better Auth |
| 037 | 22 Nov | **`application_form_opened` is recorded when the form appears in the browser**, not on server render | Link prefetch would record phantom "opened" events and distort M1 and M2 | Record on server render |
| 038 | 22 Nov | **R5 conversion is guarded in a single statement** (status unchanged and no newer status change) | A status change saved at the same moment must never be overwritten; no extra database call | Re-read before converting (extra round trip) |
| 039 | 22 Nov | **Editing the date sent moves the initial "Sent" change**; the new date cannot be after the next change | Keeps the history and response times (R1/R4/R5) consistent while still letting students fix mistakes | Leave history unchanged; lock the date sent once there are replies |
| 040 | 22 Nov | **A reminder, once shown, stays until the student reacts**, even if the company median changes | One reminder per quiet period (R12); reminders that appear and disappear on their own would confuse students | Hide the reminder when the median rises |
| 041 | 22 Nov | **Dashboard median time to first reply needs ≥ 5 replied applications** | Same privacy reasoning as R3 and R8: with very little data, the number could come from a single student | No minimum |
| 042 | 22 Nov | **Only students can delete their account in the MVP** | US08 is a student story; Career Service accounts are created and managed by the team | Career Service self-deletion |
| 043 | 22 Nov | **Metrics use cohort maturity: M6 counts only students registered ≥ 7 days ago; M7 only activated students registered ≥ 28 days ago** | Younger accounts have not had the full window yet; counting them makes the rate look artificially low | Count all verified students |
| 044 | 22 Nov | **Add M4b: follow-up rate split by reminder reason** | Tests whether company statistics make reminders more effective than a fixed 14-day rule — the core of H3 | Only overall M4 |
| 045 | 22 Nov | **No in-app metrics page in the MVP; metrics run with `npm run metrics`** | Metrics are for the product team, not the Career Service (would need a new access decision); no real data before the pilot | Admin metrics page |
| 046 | 22 Nov | **Light theme only in the MVP** | The create-next-app dark-mode CSS made text unreadable on fixed light cards; supporting both themes properly doubles the contrast work | Proper dark mode |
| 047 | 22 Nov | **Light and dark themes with a toggle (replaces 046); visual style from the Assignment 1 mockups** | Consistency with the specification mockups; the user chooses the theme. Built with semantic design tokens so both themes are checked for WCAG AA in one test | Light theme only (046) |
| 048 | 22 Nov | **`neon-http` driver for queries and Better Auth; a WebSocket `Pool` opened and closed inside each transaction (`withTransaction`)**. Supersedes 032 for the app; migrations still use the direct connection | On Vercel a pooled WebSocket outlived the request and the next query failed on a dead socket (production, 22 Nov); Neon says Pool connections must not outlive a request. Transactions keep the same guarantees on their own connection; a test forbids `db.transaction(` outside `db/client.ts` | Global `Pool` with `maxUses: 1`; Pool per request; `attachDatabasePool` (new dependency); retry on connection errors |
